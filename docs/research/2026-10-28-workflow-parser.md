# What GitHub's workflow parser and expressions libraries give us in a browser

Research for ticket #2 (map #1, WhyNoRun). Date: 2026-10-28.

**Versions examined:** `@actions/workflow-parser@0.3.61` and `@actions/expressions@0.3.61` (both published 2026-08-04, the latest on npm). The source is `actions/languageservices` at commit [`4043eda`](https://github.com/actions/languageservices/tree/4043eda158e16579cc5fb1b0b07a4bce2a76f0b5), the head of `main` (2026-08-05). In the citations below, `LS@4043eda/<path>#Ln` means `https://github.com/actions/languageservices/blob/4043eda158e16579cc5fb1b0b07a4bce2a76f0b5/<path>#Ln`. `DOCS/<path>` means `https://github.com/github/docs/blob/main/<path>`.

**Method:** I installed both packages in a scratch directory outside the repo and read their `dist/*.d.ts` and the upstream `src/`. I parsed sample workflows and evaluated `if:` and concurrency expressions in Node 26.12.1. I built a Vite 8.3.5 browser bundle, ran it in headless Chrome, and measured it with an esbuild 0.28.2 metafile. Claims marked **[ran]** come from running the code. Claims marked **[read]** come from reading the source or docs. Claims marked **[inferred]** are my conclusions and were not run. Two independent reviews followed; their corrections are folded in below and listed under "Verification notes".

## 1. Public API and stability

- **Two-step pipeline.** `parseWorkflow(file, trace)` reads the YAML into a tree of `TemplateToken`s and validates it against the workflow schema bundled in the package. `convertWorkflowTemplate(context, root, fileProvider?, options?)` then turns that tree into a `WorkflowTemplate` object. [read] [`workflow-parser/README.md` § Usage](https://github.com/actions/languageservices/blob/4043eda158e16579cc5fb1b0b07a4bce2a76f0b5/workflow-parser/README.md); `LS@4043eda/workflow-parser/src/index.ts#L1-L6`.
- **Malformed YAML.** If the YAML itself does not parse, `parseWorkflow` returns `value: undefined` and only the YAML errors (`LS@4043eda/workflow-parser/src/workflows/workflow-parser.ts`, early return). Passing that `undefined` to `convertWorkflowTemplate` adds a junk error ("Cannot read properties of undefined (reading 'assertMapping')"). **Guard:** if `result.value` is undefined, report the context errors and skip conversion [ran].
- **`WorkflowTemplate` shape:** `{ events: EventsConfig, jobs: WorkflowJob[], concurrency: TemplateToken, env: TemplateToken, errors?: {Message}[] }`. A job is either a `Job` or a `ReusableWorkflowJob`. Its `id` and `needs` are `StringToken`s, and its `if` is a `BasicExpressionToken`. `strategy`, `concurrency`, `environment` and `runs-on` stay as raw `TemplateToken`s. [read] `LS@4043eda/workflow-parser/src/model/workflow-template.ts#L10-L18`. [ran] My sample produced exactly the keys `events, concurrency, jobs`.
- **Not converted: `permissions`, `defaults`, `timeout-minutes`, `continue-on-error` (job level), `run-name`, `name`.** The root `switch` handles only `on`, `jobs`, `concurrency` and `env` (`LS@4043eda/workflow-parser/src/model/convert.ts#L83-L98`). The job `switch` has no `permissions` case (`LS@4043eda/workflow-parser/src/model/converter/job.ts#L46-L140`). The schema still validates `permissions`: a typo like `contentz:` reports `Unexpected value 'contentz'` at line 3, column 3 [ran]. The values themselves stay in the raw token tree (`ParseWorkflowResult.value`), where I read `permissions: {contents: read}` with line and column [ran].
- **The TS port is not the reference implementation.** Each package README says it is "just one of multiple implementations" ([workflow-parser README § Contributing](https://github.com/actions/languageservices/blob/4043eda158e16579cc5fb1b0b07a4bce2a76f0b5/workflow-parser/README.md); [expressions README § Contributing](https://github.com/actions/languageservices/blob/4043eda158e16579cc5fb1b0b07a4bce2a76f0b5/expressions/README.md)). The shared cross-implementation tests live in `workflow-parser/testdata/reader/`, and **93 of them are skipped** by the TS port ([`skipped-tests.txt`](https://github.com/actions/languageservices/blob/4043eda158e16579cc5fb1b0b07a4bce2a76f0b5/workflow-parser/testdata/skipped-tests.txt)). The skipped tests include `permissions.yml`, `job-permissions.yml`, `job-concurrency.yml`, `matrix-basic.yml`, `workflow-defaults.yml`, `preserves-source-info-*.yml` and every `reusable-workflow-*-permissions-*` case. Their expected output, which comes from the reference parser, includes a job-level `"permissions"` key ([`job-permissions.yml` L112-L120](https://github.com/actions/languageservices/blob/4043eda158e16579cc5fb1b0b07a4bce2a76f0b5/workflow-parser/testdata/reader/job-permissions.yml)). The TS port does not emit that key. [read]
- **Schema lag: the bundled schema is behind github.com.** Under the default `parseWorkflow(file, trace)` call, 0.3.61 rejects keys that GitHub documents today [ran]:
  - top-level `cache-mode` → `Unexpected value 'cache-mode'` (documented at `DOCS/content/actions/reference/workflows-and-actions/workflow-syntax.md` § `cache-mode`, L409). No flag fixes this: the key is missing from `workflow-v1.0.min.json`.
  - step keys `background`, `wait`, `wait-all`, `cancel` → `Unexpected value 'background'` / `'wait'` (documented at the same file, § `jobs.<job_id>.steps[*].background`, L1078 onwards). These are behind a feature flag (`LS@4043eda/workflow-parser/src/templates/template-reader.ts#L811`, `allowBackgroundSteps`). They parse with no errors if we build the `TemplateContext` ourselves through deep imports, set `ctx.state.featureFlags = new FeatureFlags({allowBackgroundSteps: true})` before `parseWorkflow(file, ctx)`, and pass the same `featureFlags` to `convertWorkflowTemplate` [ran].
  - The parser also **misses** a documented error: `concurrency: {group: g, queue: max, cancel-in-progress: true}` parses cleanly at both workflow and job level [ran], but GitHub says "The combination of `queue: max` and `cancel-in-progress: true` is not allowed and will result in a workflow validation error" (`DOCS/data/reusables/actions/actions-group-concurrency.md`) [read].
  - A simulator that trusts the parser's errors would call valid workflows broken and miss real errors. We need a small allow-list/downgrade layer over parser errors and our own extra checks.
- **Stability: low across minor releases.** The packages are pre-1.0: 63 releases from 0.2.0 (2023-03-23) to 0.3.61 (2026-08-04). In 2026 there were 32 releases from January to August (14 in January alone), about 4 a month on average (`npm view @actions/workflow-parser time`) [ran]. The public types churn inside 0.3.x. Diffing `dist/model/workflow-template.d.ts` from 0.3.40 to 0.3.61 [ran]:
  - `Step` grew from `ActionStep | RunStep` to also include `WaitStep | WaitAllStep | CancelStep | ParallelStep`.
  - `BaseStep.if` became optional (`if?:`), so code that assumes `step.if` breaks.
  - Added: `queue` on concurrency, `skipDeployment` on environment, `timezone` on schedule, container `entrypoint`/`command`, `background` on run/action steps, and a `featureFlags` converter option.

  The repo README says GitHub is "not taking contributions", but "will still provide security updates … and fix major breaking changes" ([README § Note](https://github.com/actions/languageservices/blob/4043eda158e16579cc5fb1b0b07a4bce2a76f0b5/README.md)) [read]. The package exports `"./*"` deep paths (`package.json` `exports`), and some useful types are reachable only that way. For example, `TemplateToken` (with its `traverse()` generator), `TemplateContext` and `ErrorPolicy` are not re-exported from the index. Importing `TemplateToken` from the root fails in esbuild ("No matching export"), while `@actions/workflow-parser/templates/tokens/template-token` works [ran]. GitHub's own language service also uses these deep imports (`LS@4043eda/languageservice/src/context-providers/matrix.ts#L1-L5`) [read]. **Confidence: high** that the API shape is usable. **Low** that it stays stable across minor releases. Pin an exact version (no `^`), handle unknown `Step` kinds with a `default` branch, and diff the `.d.ts` files on every upgrade.

## 2. Positions (YAML line and column)

- Every `TemplateToken` has `range: {start, end}` with one-based `line` and `column`, plus `.line` and `.col` getters (`LS@4043eda/workflow-parser/src/templates/tokens/token-range.ts#L1-L10`) [read].
- [ran] Ranges came back for job ids (`test` → 20:3–20:7), explicit `if:` (`deploy` → 40:9–40:116), job and workflow `concurrency` group expressions (17:10–17:30), step `if`, the raw `permissions` mapping (15:3), and raw `on.push.branches` items (`'release/**'` → 5:9–5:21).
- **Gaps:**
  1. A job or step **without** an `if:` gets a synthetic `success()` token with `range: undefined`. For jobs this is `LS@4043eda/workflow-parser/src/model/converter/job.ts#L149` (reusable) and `#L166` (normal); for steps it is `LS@4043eda/workflow-parser/src/model/converter/steps.ts#L144` (run) and `#L156` (uses) [read+ran]. A Verdict for an implicit condition must point at the job or step key instead.
  2. `events` is converted to **plain strings** (`branches?: string[]`, `LS@4043eda/workflow-parser/src/model/workflow-template.ts#L130-L180`). A filter Verdict therefore has to look up its line in the raw token tree with `TemplateToken.traverse` [ran].
  3. `WorkflowTemplate.errors` holds only `{Message}`, with no range. Use `result.context.errors.getErrors()`, whose `TemplateValidationError.range` is set, as in `bad.yml (Line: 3, Col: 5): Unexpected value 'branchez'` [ran].
  4. Step ids are synthesized (`__run`, `__actions_checkout`) [ran].
  5. **An aliased node reports its anchor's position.** GitHub supports YAML anchors and aliases in workflows (`DOCS/content/actions/reference/workflows-and-actions/reusing-workflow-configurations.md` § YAML anchors and aliases) [read]. Aliases resolve correctly, but the resolved tokens keep the anchor's range: with `if: &cond …` on job `a` (line 4) and `if: *cond` on job `b` (line 8), job `b`'s `if.range.start` is 4:15, inside job `a` [ran] (`LS@4043eda/workflow-parser/src/workflows/yaml-object-reader.ts#L92`). The same applies to aliased steps and whole jobs [inferred from the same code path]. The position index must notice a token whose range falls outside its parent job's span and point the Verdict at the alias site, which means reading the alias position from the `yaml` CST, because the token tree drops it. YAML merge keys (`<<: *base`) are rejected with `Unexpected value '<<'` [ran]; whether github.com accepts them is untested.

## 3. Expressions

- **Evaluation works against contexts we supply.** `new Lexer(src).lex()` → `new Parser(tokens, contextNames, extraFunctions).parse()` → `new Evaluator(expr, contextDict, functionsMap).evaluate()`. To build the contexts, `JSON.parse(JSON.stringify(obj), data.reviver)` turns plain JSON into `ExpressionData` [read: `expressions/dist/data/reviver.d.ts`; README § With context data]. [ran] Results:
  - Job `if`: `success() && (github.event_name == 'push' && github.ref == 'refs/heads/main' && !github.event.pull_request.head.repo.fork)`, with a fork `pull_request` context → `false`.
  - Concurrency: `ci-${{ github.ref }}` is rewritten by the parser into `format('ci-{0}', github.ref)`, which evaluates to `ci-refs/pull/7/merge`. The parser does this rewrite itself, so any interpolated string becomes one expression.
  - Matrix: `matrix.os == 'ubuntu-latest' && contains(fromJSON('["a","b"]'), 'b')` → `true`.
  - A missing path such as `github.event.nope.deeper` evaluates to `Null` and does not throw, matching GitHub's behaviour.
- **Built-in functions:** only `case`, `contains`, `endsWith`, `format`, `fromJSON`, `join`, `startsWith` and `toJSON` (`LS@4043eda/expressions/src/funcs.ts#L19`). `case()` is built in and parses and evaluates with no flag set: `case(true,'a','b')` → `'a'`, and the workflow schema accepts it in a job-level `if` [ran]. The `allowCaseFunction` flag only controls whether autocompletion suggests it (`LS@4043eda/expressions/src/completion.ts#L100`) [read].
- **Status functions `success()`, `failure()`, `cancelled()`, `always()` and `hashFiles()` are not implemented.** The `Unrecognized function: 'success'` error comes from the **Parser** (`LS@4043eda/expressions/src/funcs.ts#L30-L40`), which checks built-ins and then its `extensionFunctions` list. So each stub (`{name, minArgs, maxArgs, call}`) must be registered **in two places** [ran]:
  - in `new Parser(tokens, contexts, [stubs])` so it validates. A stub only in the Evaluator's map still gives `ExpressionError: Unrecognized function: 'success'`;
  - in `new Evaluator(expr, ctx, new Map([[name, stub]]))` so it runs. The Evaluator checks its map before the built-ins (`LS@4043eda/expressions/src/evaluator.ts#L162`). A stub only in the Parser fails at evaluation with `TypeError: Cannot read properties of undefined (reading 'call')`.

  The schema gives each function's arity per context: `job-if` allows `always(0,0)`, `failure(0,MAX)`, `cancelled(0,0)`, `success(0,MAX)`, and **not** `hashFiles`, which appears only in step-level contexts (`LS@4043eda/workflow-parser/src/workflow-v1.0.json#L1863-L1876`, `#L2314`) [read]. In WhyNoRun, `success()`/`failure()` must be computed from the simulated `needs` results, `cancelled()` from the simulated concurrency outcome, and `always()` returns true. `hashFiles()` is not needed for job-level decisions. A step-level `hashFiles()` needs a scenario-supplied value or an "unknown" result.
- **The implicit `success() &&` wrap is done for us.** `convertToIfCondition` and `ensureStatusFunction` wrap any `if` that contains no status function as `success() && (…)`, and an empty `if` becomes `success()` (`LS@4043eda/workflow-parser/src/model/converter/if-condition.ts#L21-L37`, `#L81`) [read+ran]. This matches GitHub's documented default ([Expressions § Status check functions](https://docs.github.com/en/actions/reference/workflows-and-actions/expressions#status-check-functions)) [read].
- **Context checks are free.** The schema rejects contexts that a position does not allow. For example, `secrets` in a job-level `if` gives `Unrecognized named-value: 'secrets'` at 4:9 [ran]. Job `if` allows `github, inputs, vars, needs` (schema L1865–L1872). Job `concurrency` allows `github, inputs, vars, needs, strategy, matrix` [read: `workflow-v1.0.min.json` `job-concurrency`].
- **No library evaluates a token tree.** `runs-on`, `environment`, `strategy` (including matrix entries and `include: ${{ fromJSON(…) }}`), workflow-level `concurrency`, `with` and `env` all stay as Mapping, Sequence or String tokens with nested `BasicExpressionToken`s. Neither `workflow-parser` nor `languageservice` creates an `Evaluator` for template tokens (in the installed dist, `new Evaluator` appears only in `expressions/dist/completion.js` [ran]; upstream also in `languageservice/src/expression-hover/visitor.ts` [read]). We must write a **template-token evaluator**: walk Mapping/Sequence/Literal tokens, evaluate each `BasicExpressionToken` through Lexer → Parser → Evaluator, and convert the resulting `ExpressionData` back to JSON. A whole-value `${{ }}` can return an object or array (a `fromJSON` matrix or `include`). Matrix expansion depends on it [read+inferred].
- **Concurrency.** `cancel-in-progress` as an expression is skipped by `convertConcurrency`, which only reads a literal boolean (`LS@4043eda/workflow-parser/src/model/converter/concurrency.ts#L9`, `#L19`, `#L27`). Because `WorkflowTemplate.concurrency` keeps the raw token, we evaluate that token ourselves [read+ran]. GitHub's model also has rules the parser does not apply (`DOCS/data/reusables/actions/actions-group-concurrency.md`) [read]:
  - group names are **case-insensitive** (`prod` = `Prod`);
  - `queue: single` (default) keeps at most one pending run and replaces it; `queue: max` keeps up to 100 pending runs and cancels any beyond that. The job-level converter reads `queue` (`concurrency.ts#L26-L30`); the workflow-level `concurrency` stays raw;
  - `queue: max` with `cancel-in-progress: true` is a validation error that the parser does not report (see §1).

## 4. Browser fit

- **Format:** ESM only (`"type": "module"`; `exports` has only an `import` condition), with TypeScript `.d.ts` files [read: `package.json`]. The licence is MIT for both packages and for the repo ([LICENSE](https://github.com/actions/languageservices/blob/4043eda158e16579cc5fb1b0b07a4bce2a76f0b5/LICENSE)). Dependencies: workflow-parser needs `@actions/expressions`, `yaml@^2` (ISC; it ships a `browser` build through `exports.default`) and `cronstrue` (MIT). `@actions/expressions` has **no dependencies** [ran: `npm view`].
- **It runs in a real browser.** A Vite 8.3.5 production build of "parse + convert + evaluate" gave **288.4 KB minified / 74.7 KB gzip** with no Node built-in warnings (a reviewer's rebuild gave 287.0 / 74.1 KB). I loaded it in headless Chrome and it printed `jobs=test,deploy,notify errors=[] eval=true` [ran]. Size breakdown from the esbuild metafile: workflow-parser 136 KB (72 KB of it is the bundled `workflow-v1.0.min.json` schema), yaml 95 KB, expressions 22.5 KB, cronstrue 21 KB [ran]. GitHub hosts its own browser playground, which runs the full language server in a web worker with Monaco ([`browser-playground/README.md`](https://github.com/actions/languageservices/blob/4043eda158e16579cc5fb1b0b07a4bce2a76f0b5/browser-playground/README.md); <https://actions.github.com/languageservices>) [read].
- **Hostile YAML can freeze the tab.** `YamlObjectReader.getNodes` resolves every alias by walking the anchored node again (`LS@4043eda/workflow-parser/src/workflows/yaml-object-reader.ts#L58-L110`, alias at L92). It guards against cycles but does not count expansions; the `yaml` library's `maxAliasCount` applies only to `toJS`, not to this walk. Nested levels of ten aliases each: 3/4/5 levels took 88/623/7231 ms in `parseWorkflow` on Node 26.12.1, from a 354-byte file at level 5 [ran] (a reviewer measured 10.7 s at 6 levels from 402 bytes). Each level multiplies the time by about 10. **Guard:** pre-check with `yaml.parseDocument(src).toJS({maxAliasCount: N})` and reject before `parseWorkflow`, and/or parse in a Web Worker that the main thread terminates on a timeout. Apply the same pre-check in the CLI [inferred].
- **Plain Node ESM cannot import `@actions/workflow-parser` 0.3.61.** It does `import WorkflowSchema from "../workflow-v1.0.min.json"` without `with {type: "json"}` (`LS@4043eda/workflow-parser/src/workflows/workflow-schema.ts#L3`). Node 26 throws `ERR_IMPORT_ATTRIBUTE_MISSING` [ran]. This is open upstream as [actions/languageservices#387](https://github.com/actions/languageservices/issues/387), filed 2026-08-12 with no reply. **Workaround [ran]:** bundle the CLI with esbuild. With `--platform=node --format=esm`, a `createRequire` banner is also needed, because `yaml`'s Node entry is CommonJS and calls `require("process")`. Vite and Vitest resolve JSON imports natively, so the playground and tests are unaffected [inferred: Vite build ran; Vitest not run].

## 5. Coverage

- **`on:` shapes:** a string (`on: push`), a list (`[push, pull_request]`) and a mapping all convert to `EventsConfig` [ran]. Filters come through as plain arrays: `branches`, `branches-ignore`, `tags`, `tags-ignore`, `paths`, `paths-ignore`, `types`, `workflows`, plus `workflow_dispatch` and `workflow_call` inputs and secrets (`workflow-template.ts#L130-L232`) [read+ran]. Unknown events (`pushh`) and invalid cron (`61 * * * *`) are reported with positions [ran]. **Filter *matching* (glob semantics for `**`, `!`, path filters) is not in the library** [read: no matcher in `dist/`]. We build it.
  - **Default activity types are not filled in.** `on: pull_request:` with no keys converts to `{"pull_request":{}}` [ran]. GitHub runs `pull_request` and `pull_request_target` only for `opened`, `synchronize` and `reopened` when `types` is absent (`DOCS/content/actions/reference/workflows-and-actions/events-that-trigger-workflows.md` L465, L672) [read]. Event matching must apply these defaults.
  - **`schedule[].timezone` is converted but never validated.** `timezone: Not/AZone` gives no error [ran]. GitHub expects an IANA zone, and during a DST spring-forward a schedule in a skipped hour runs at the next valid time (`DOCS/data/reusables/repositories/actions-scheduled-workflow-example.md`) [read]. Validate with `Intl.supportedValuesOf('timeZone')` [inferred].
- **Reusable workflows (`workflow_call`):** a `uses:` job becomes `ReusableWorkflowJob` with `ref`, `input-values`, `secret-values` and `inherit-secrets` [ran]. With `fetchReusableWorkflowDepth: 1` and a `FileProvider`, the converter fetches the callee and fills in `input-definitions`, `secret-definitions` and nested `jobs` (`LS@4043eda/workflow-parser/src/model/converter/job.ts#L143-L159`). Both `./path` and `$/path` (same-repo) refs reach the provider as `{path}`; for `./…` the provider received `{path: ".github/workflows/deploy.yml"}` [ran] (`LS@4043eda/workflow-parser/src/workflows/file-reference.ts#L15-L27`) [read]. **Only depth 0 or 1 is supported** (`LS@4043eda/workflow-parser/src/model/convert.ts#L31`). Remote refs parse to `{owner, repository, path, version}`. We need our own provider for those, such as a fetch from the GitHub API or a user upload. Permission checks between caller and callee are among the skipped tests, so they are not implemented [read]. **GitHub's limits for the simulator to enforce** (`DOCS/content/actions/reference/workflows-and-actions/reusing-workflow-configurations.md` L58-L59, L110) [read]: up to 10 levels of nesting and at most 50 unique reusable workflows per caller tree on github.com (GHES: 4 and 20); `GITHUB_TOKEN` permissions can stay the same or become more restrictive down a chain, never broader.
- **Matrix `include`/`exclude`:** **not expanded.** `strategy` stays a raw token [ran], and the reference test output also keeps it raw (`testdata/reader/matrix-basic.yml`) [read]. The language service only derives matrix *keys* for completion (`LS@4043eda/languageservice/src/context-providers/matrix.ts#L9`, doc comment L46–L97) [read]. A `${{ fromJSON(...) }}` matrix parses with no error and stays an expression [ran]. We build the Cartesian product plus include/exclude ourselves, on top of the template-token evaluator (§3).
- **Errors and `ErrorPolicy`.** Schema errors come with line and column. Converter errors (bad `if` expressions, unknown `needs`, dependency cycles) are reported **under the default policy** whenever the YAML passes schema validation: `Unexpected end of expression: '=='` and `Job 'b' depends on unknown job 'missing'.` appeared identically under both policies [ran]. The policies differ only when a schema error is present: the default `ErrorPolicy.ReturnErrorsOnly` then returns only the schema errors and no `events` or `jobs`, while `ErrorPolicy.TryConversion` (value 1) continues and reports both (`LS@4043eda/workflow-parser/src/model/convert.ts#L65-L70`, and the `finally` block near L130-L135) [read+ran]. **Use `TryConversion`** so one bad key does not hide the other errors. `ErrorPolicy` is declared in `model/convert.d.ts` but not re-exported from the index, so pass the number or deep-import it [read].
- **Dependency cycles have two different messages** [ran]: `The workflow must contain at least one job with no dependencies.` only when every job is in the cycle; otherwise one positioned error per edge, e.g. `Job 'a' depends on job 'b' which creates a cycle in the dependency graph.` (7:16 and 11:12 in my test). WhyNoRun should not classify errors by message text; it should run its own graph check where it needs structure [inferred].
- **Composite actions.** The same package ships an `action.yml` parser (`parseAction`, `convertActionTemplate`, `ActionRunsComposite/Node/Docker`) in `dist/actions/`. Because of the `"./*"` export map it is imported as `@actions/workflow-parser/actions/index`; the shorter `@actions/workflow-parser/actions` does not resolve [ran: esbuild]. It matters when a step's `uses: ./local-action` is a composite action whose own steps or `if:`s affect the outcome. Out of MVP scope; listed as an expansion.

## 6. Who uses them

- **`github/vscode-github-actions`** (the official VS Code extension, v0.32.3) depends on `@actions/languageserver ^0.3.60` and `@actions/workflow-parser ^0.3.60` ([`package.json` L585-L586](https://github.com/github/vscode-github-actions/blob/main/package.json)) [read].
- **`@actions/languageservice`** builds on both. Two pieces are worth borrowing: `context-providers/*.ts` builds the `github`, `needs`, `matrix`, `secrets` and other contexts as `DescriptionDictionary`s, and `utils/validate-if.ts` flags `if:` conditions like `format('push == {0}', …)` that are always true. That second check fits WhyNoRun's "explain the skip" job directly (`LS@4043eda/languageservice/src/utils/validate-if.ts#L19`) [read]. I found no consumer that *evaluates* a whole workflow run or a template token tree. That part is ours to build [inferred, from repo code search for `new Evaluator`: only `expressions/` and `languageservice/src/expression-hover/visitor.ts`].

## Verdict for the map

**Use both packages. They are the right foundation, and they run in the browser today. Treat them as a parser, validator and expression engine, not as a simulator, and not as the final word on what github.com accepts.**

**What we get for free (high confidence, all run):**
- YAML → validated token tree, using GitHub's published TS schema (which lags github.com, see risks). Errors (unknown keys, bad cron, bad permission names, disallowed contexts, unknown `needs`, dependency cycles, malformed expressions) come with one-based line and column. Use `ErrorPolicy.TryConversion` to get schema and converter errors together.
- Typed `on:` events and filters, jobs, `needs`, reusable-workflow calls (depth 1 through our `FileProvider`), and concurrency tokens.
- `if:` already normalized with GitHub's implicit `success() &&` wrap. Interpolated strings are rewritten into `format()` expressions.
- A zero-dependency expression evaluator that takes our own `github/inputs/vars/secrets/needs/matrix` contexts and accepts our own function implementations (registered with both Parser and Evaluator).
- A browser bundle of about 75 KB gzip under Vite. MIT/ISC licences.

**What we must build:**
1. **Status functions** (`success`, `failure`, `cancelled`, `always`), registered with both the Parser and the Evaluator, driven by the simulated `needs` results and concurrency outcome, plus a `hashFiles` stub for step-level `if`.
2. **A template-token evaluator** for `runs-on`, `environment`, `strategy`/matrix, workflow `concurrency`, `with` and `env`, returning JSON (objects and arrays included).
3. **Matrix expansion** (product, `include`, `exclude`, `fromJSON` matrices driven by the scenario), on top of item 2.
4. **Event and filter matching** (branch, tag and path globs; `types`, with the default `opened/synchronize/reopened` for `pull_request` and `pull_request_target`; fork PR vs `pull_request_target` semantics; schedule `timezone` validation and DST rule).
5. **Concurrency outcome**: case-insensitive group names, `queue: single` vs `queue: max` (100 pending), and our own error for `queue: max` + `cancel-in-progress: true`.
6. **Permissions model.** Read `permissions` and `defaults` from the raw token tree. The converter drops them, and caller/callee permission rules are not implemented.
7. **A position index for Verdicts.** Walk the raw tokens for filter lines, fall back to the job or step key when an `if` is implicit, and map aliased nodes back to the alias site via the `yaml` CST.
8. **A schema-lag layer**: enable `allowBackgroundSteps`, and allow-list or downgrade parser errors for keys GitHub documents but the schema rejects (e.g. `cache-mode`).
9. **Input guards**: skip conversion when `result.value` is undefined, and reject alias bombs (`maxAliasCount` pre-check and/or a terminable Web Worker).
10. **A FileProvider** for remote reusable workflows, our own handling for depth > 1, and GitHub's limits (10 levels, 50 unique workflows; GHES 4 and 20; permissions only narrow).
11. **A CLI build step** (esbuild bundle) until upstream issue #387 is fixed.

**Possible expansions (out of MVP scope):**
- Composite actions through the bundled `action.yml` parser (`@actions/workflow-parser/actions/index`), so a local composite action's own `if:`s can be explained.
- Simulating background, `wait`, `wait-all`, `cancel` and `parallel` step semantics (the MVP only needs them to parse).
- YAML merge keys (`<<:`), once we know whether github.com accepts them.
- A GHES mode with GHES limits and the `queue`-less concurrency model.

**Risks:**
- **Divergence from GitHub's real parser.** 93 shared conformance tests are skipped in the TS port, and the bundled schema both rejects documented keys and misses a documented error. Mitigation: pin the exact version, add our own golden tests, run the schema-lag layer, and phrase Verdicts as "per GitHub's published parser".
- **API churn and maintenance mode.** Minor releases change public types (`Step` union, optional `if`), deep imports are needed, and the upstream repo takes no contributions. Mitigation: exact version pin, one adapter module in the core, exhaustive switches with a default, and a `.d.ts` diff on every upgrade.
- **Alias bombs** can freeze the browser tab or the CLI. Mitigation: guards in must-build item 9.
- **Misplaced positions for aliased nodes** can point a Verdict at the wrong job. Mitigation: must-build item 7.
- **The Node ESM import bug (#387)** breaks a naive `node` CLI. The bundling workaround has been verified.
- **Bundle weight** (~75 KB gzip) is fine for a playground. Lazy-loading the parser keeps first paint light if needed [inferred].

**Unverified:** Vitest running the package directly (expected to work, because Vite handles JSON imports). Behaviour of versions newer than 0.3.61 (none existed on 2026-10-28). Whether `failure(jobId)` and `success(jobId)` arguments (allowed in `job-if`) need special handling in our stubs. Whether github.com accepts YAML merge keys. Aliased steps and whole aliased jobs were not run separately (same code path as the aliased `if`).
