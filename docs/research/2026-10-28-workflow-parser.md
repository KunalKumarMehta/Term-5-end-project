# What GitHub's workflow parser and expressions libraries give us in a browser

Research for ticket #2 (map #1, WhyNoRun). Date: 2026-10-28.

**Versions examined:** `@actions/workflow-parser@0.3.61` and `@actions/expressions@0.3.61` (both published 2026-08-04, the latest on npm). The source is `actions/languageservices` at commit [`4043eda`](https://github.com/actions/languageservices/tree/4043eda158e16579cc5fb1b0b07a4bce2a76f0b5), the head of `main` (2026-08-05). In the citations below, `LS@4043eda/<path>#Ln` means `https://github.com/actions/languageservices/blob/4043eda158e16579cc5fb1b0b07a4bce2a76f0b5/<path>#Ln`.

**Method:** I installed both packages in a scratch directory outside the repo and read their `dist/*.d.ts` and the upstream `src/`. I parsed a sample workflow and evaluated `if:` and concurrency expressions in Node 26.12.1. I built a Vite 8.3.5 browser bundle, ran it in headless Chrome, and measured it with an esbuild 0.28.2 metafile. Claims marked **[ran]** come from running the code. Claims marked **[read]** come from reading the source or docs. Claims marked **[inferred]** are my conclusions and were not run.

---

## 1. Public API and stability

- **Two-step pipeline.** `parseWorkflow(file, trace)` reads the YAML into a tree of `TemplateToken`s and validates it against GitHub's workflow schema. `convertWorkflowTemplate(context, root, fileProvider?, options?)` then turns that tree into a `WorkflowTemplate` object. [read] [`workflow-parser/README.md` § Usage](https://github.com/actions/languageservices/blob/4043eda158e16579cc5fb1b0b07a4bce2a76f0b5/workflow-parser/README.md); `LS@4043eda/workflow-parser/src/index.ts#L1-L6`.
- **`WorkflowTemplate` shape:** `{ events: EventsConfig, jobs: WorkflowJob[], concurrency: TemplateToken, env: TemplateToken, errors?: {Message}[] }`. A job is either a `Job` or a `ReusableWorkflowJob`. Its `id` and `needs` are `StringToken`s, and its `if` is a `BasicExpressionToken`. `strategy`, `concurrency`, `environment` and `runs-on` stay as raw `TemplateToken`s. [read] `LS@4043eda/workflow-parser/src/model/workflow-template.ts#L10-L18`. [ran] My sample produced exactly the keys `events, concurrency, jobs`.
- **Not converted: `permissions`, `defaults`, `timeout-minutes`, `continue-on-error` (job level), `run-name`, `name`.** The root `switch` handles only `on`, `jobs`, `concurrency` and `env` (`LS@4043eda/workflow-parser/src/model/convert.ts#L83-L98`). The job `switch` has no `permissions` case (`LS@4043eda/workflow-parser/src/model/converter/job.ts#L46-L140`). The schema still validates `permissions`: a typo like `contentz:` reports `Unexpected value 'contentz'` at line 3, column 3 [ran]. The values themselves stay in the raw token tree (`ParseWorkflowResult.value`), where I read `permissions: {contents: read}` with line and column [ran].
- **The TS port is not the reference implementation.** Each package README says it is "just one of multiple implementations" ([workflow-parser README § Contributing](https://github.com/actions/languageservices/blob/4043eda158e16579cc5fb1b0b07a4bce2a76f0b5/workflow-parser/README.md); [expressions README § Contributing](https://github.com/actions/languageservices/blob/4043eda158e16579cc5fb1b0b07a4bce2a76f0b5/expressions/README.md)). The shared cross-implementation tests live in `workflow-parser/testdata/reader/`, and **93 of them are skipped** by the TS port ([`skipped-tests.txt`](https://github.com/actions/languageservices/blob/4043eda158e16579cc5fb1b0b07a4bce2a76f0b5/workflow-parser/testdata/skipped-tests.txt)). The skipped tests include `permissions.yml`, `job-permissions.yml`, `job-concurrency.yml`, `matrix-basic.yml`, `workflow-defaults.yml`, `preserves-source-info-*.yml` and every `reusable-workflow-*-permissions-*` case. Their expected output, which comes from the reference parser, includes a job-level `"permissions"` key ([`job-permissions.yml` L112-L120](https://github.com/actions/languageservices/blob/4043eda158e16579cc5fb1b0b07a4bce2a76f0b5/workflow-parser/testdata/reader/job-permissions.yml)). The TS port does not emit that key. [read]
- **Stability.** The packages are pre-1.0: 63 releases from 0.2.0 (2023-03-23) to 0.3.61 (2026-08-04), roughly monthly in 2026 (`npm view @actions/workflow-parser time`; [releases](https://github.com/actions/languageservices/releases)) [ran]. The repo README says GitHub is "not taking contributions", but "will still provide security updates … and fix major breaking changes" ([README § Note](https://github.com/actions/languageservices/blob/4043eda158e16579cc5fb1b0b07a4bce2a76f0b5/README.md)) [read]. The package exports `"./*"` deep paths (`package.json` `exports`), and some useful types are reachable only that way. For example, `TemplateToken` (with its `traverse()` generator) is not re-exported from the index. Importing it from the root fails in esbuild ("No matching export"), while `@actions/workflow-parser/templates/tokens/template-token` works [ran]. GitHub's own language service also uses these deep imports (`LS@4043eda/languageservice/src/context-providers/matrix.ts#L1-L5`) [read]. **Confidence: high** that the API shape is usable. **Medium** that it stays stable: the major version is 0, deep paths are internal, and there is no semver promise.

## 2. Positions (YAML line and column)

- Every `TemplateToken` has `range: {start, end}` with one-based `line` and `column`, plus `.line` and `.col` getters (`LS@4043eda/workflow-parser/src/templates/tokens/token-range.ts#L1-L10`) [read].
- [ran] Ranges came back for job ids (`test` → 20:3–20:7), explicit `if:` (`deploy` → 40:9–40:116), job and workflow `concurrency` group expressions (17:10–17:30), step `if`, the raw `permissions` mapping (15:3), and raw `on.push.branches` items (`'release/**'` → 5:9–5:21).
- **Gaps:**
  1. A job or step **without** an `if:` gets a synthetic `success()` token with `range: undefined` (`LS@4043eda/workflow-parser/src/model/converter/job.ts#L149`, `#L166`) [read+ran]. A Verdict for an implicit condition must point at the job key instead.
  2. `events` is converted to **plain strings** (`branches?: string[]`, `LS@4043eda/workflow-parser/src/model/workflow-template.ts#L130-L180`). A filter Verdict therefore has to look up its line in the raw token tree with `TemplateToken.traverse` [ran].
  3. `WorkflowTemplate.errors` holds only `{Message}`, with no range. Use `result.context.errors.getErrors()`, whose `TemplateValidationError.range` is set, as in `bad.yml (Line: 3, Col: 5): Unexpected value 'branchez'` [ran].
  4. Step ids are synthesized (`__run`, `__actions_checkout`) [ran].

## 3. Expressions

- **Evaluation works against contexts we supply.** `new Lexer(src).lex()` → `new Parser(tokens, contextNames, extraFunctions).parse()` → `new Evaluator(expr, contextDict, functionsMap).evaluate()`. To build the contexts, `JSON.parse(JSON.stringify(obj), data.reviver)` turns plain JSON into `ExpressionData` [read: `expressions/dist/data/reviver.d.ts`; README § With context data]. [ran] Results:
  - Job `if`: `success() && (github.event_name == 'push' && github.ref == 'refs/heads/main' && !github.event.pull_request.head.repo.fork)`, with a fork `pull_request` context → `false`.
  - Concurrency: `ci-${{ github.ref }}` is rewritten by the parser into `format('ci-{0}', github.ref)`, which evaluates to `ci-refs/pull/7/merge`. The parser does this rewrite itself, so any interpolated string becomes one expression.
  - Matrix: `matrix.os == 'ubuntu-latest' && contains(fromJSON('["a","b"]'), 'b')` → `true`.
  - A missing path such as `github.event.nope.deeper` evaluates to `Null` and does not throw, matching GitHub's behaviour.
- **Built-in functions:** only `case`, `contains`, `endsWith`, `format`, `fromJSON`, `join`, `startsWith` and `toJSON` (`LS@4043eda/expressions/src/funcs.ts#L19`). `case()` sits behind the `allowCaseFunction` feature flag (`expressions/dist/features.d.ts`) [read].
- **Status functions `success()`, `failure()`, `cancelled()`, `always()` and `hashFiles()` are not implemented.** Without stubs, the parser throws `ExpressionError: Unrecognized function: 'success'` (and the same for `hashFiles`) [ran]. The evaluator takes a `functions` map that is checked before the built-ins (`LS@4043eda/expressions/src/evaluator.ts#L162`). I supplied stubs (`{name, minArgs, maxArgs, call}`) and they worked [ran]. The schema gives each function's arity per context: `job-if` allows `always(0,0)`, `failure(0,MAX)`, `cancelled(0,0)`, `success(0,MAX)`, and **not** `hashFiles`, which appears only in step-level contexts (`LS@4043eda/workflow-parser/src/workflow-v1.0.json#L1863-L1876`, `#L2314`) [read]. In WhyNoRun, `success()`/`failure()` must be computed from the simulated `needs` results, `cancelled()` from the simulated concurrency outcome, and `always()` returns true. `hashFiles()` is not needed for job-level decisions. A step-level `hashFiles()` needs a scenario-supplied value or an "unknown" result.
- **The implicit `success() &&` wrap is done for us.** `convertToIfCondition` and `ensureStatusFunction` wrap any `if` that contains no status function as `success() && (…)`, and an empty `if` becomes `success()` (`LS@4043eda/workflow-parser/src/model/converter/if-condition.ts#L21-L37`, `#L81`) [read+ran]. This matches GitHub's documented default ([Expressions § Status check functions](https://docs.github.com/en/actions/reference/workflows-and-actions/expressions#status-check-functions)) [read].
- **Context checks are free.** The schema rejects contexts that a position does not allow. For example, `secrets` in a job-level `if` gives `Unrecognized named-value: 'secrets'` at 4:9 [ran]. Job `if` allows `github, inputs, vars, needs` (schema L1865–L1872). Job `concurrency` allows `github, inputs, vars, needs, strategy, matrix` [read: `workflow-v1.0.min.json` `job-concurrency`].
- **`cancel-in-progress` as an expression** is skipped by `convertConcurrency`, which only reads a literal boolean (`LS@4043eda/workflow-parser/src/model/converter/concurrency.ts#L9`, `#L19`, `#L27`). Because `WorkflowTemplate.concurrency` keeps the raw token, we evaluate that token ourselves [read+ran].

## 4. Browser fit

- **Format:** ESM only (`"type": "module"`; `exports` has only an `import` condition), with TypeScript `.d.ts` files [read: `package.json`]. The licence is MIT for both packages and for the repo ([LICENSE](https://github.com/actions/languageservices/blob/4043eda158e16579cc5fb1b0b07a4bce2a76f0b5/LICENSE)). Dependencies: workflow-parser needs `@actions/expressions`, `yaml@^2` (ISC; it ships a `browser` build through `exports.default`) and `cronstrue` (MIT). `@actions/expressions` has **no dependencies** [ran: `npm view`].
- **It runs in a real browser.** A Vite 8.3.5 production build of "parse + convert + evaluate" gave **288.4 KB minified / 74.7 KB gzip** with no Node built-in warnings. I loaded it in headless Chrome and it printed `jobs=test,deploy,notify errors=[] eval=true` [ran]. Size breakdown from the esbuild metafile: workflow-parser 136 KB (72 KB of it is the bundled `workflow-v1.0.min.json` schema), yaml 95 KB, expressions 22.5 KB, cronstrue 21 KB [ran]. GitHub hosts its own browser playground, which runs the full language server in a web worker with Monaco ([`browser-playground/README.md`](https://github.com/actions/languageservices/blob/4043eda158e16579cc5fb1b0b07a4bce2a76f0b5/browser-playground/README.md); <https://actions.github.com/languageservices>) [read].
- **Plain Node ESM cannot import `@actions/workflow-parser` 0.3.61.** It does `import WorkflowSchema from "../workflow-v1.0.min.json"` without `with {type: "json"}` (`LS@4043eda/workflow-parser/src/workflows/workflow-schema.ts#L3`). Node 26 throws `ERR_IMPORT_ATTRIBUTE_MISSING` [ran]. This is open upstream as [actions/languageservices#387](https://github.com/actions/languageservices/issues/387), filed 2026-08-12 with no reply. **Workaround [ran]:** bundle the CLI with esbuild. With `--platform=node --format=esm`, a `createRequire` banner is also needed, because `yaml`'s Node entry is CommonJS and calls `require("process")`. Vite and Vitest resolve JSON imports natively, so the playground and tests are unaffected [inferred: Vite build ran; Vitest not run].

## 5. Coverage

- **`on:` shapes:** a string (`on: push`), a list (`[push, pull_request]`) and a mapping all convert to `EventsConfig` [ran]. Filters come through as plain arrays: `branches`, `branches-ignore`, `tags`, `tags-ignore`, `paths`, `paths-ignore`, `types`, `workflows`, plus `workflow_dispatch` and `workflow_call` inputs and secrets (`workflow-template.ts#L130-L232`) [read+ran]. Unknown events (`pushh`) and invalid cron (`61 * * * *`) are reported with positions [ran]. **Filter *matching* (glob semantics for `**`, `!`, path filters) is not in the library** [read: no matcher in `dist/`]. We build it.
- **Reusable workflows (`workflow_call`):** a `uses:` job becomes `ReusableWorkflowJob` with `ref`, `input-values`, `secret-values` and `inherit-secrets` [ran]. With `fetchReusableWorkflowDepth: 1` and a `FileProvider`, the converter fetches the callee and fills in `input-definitions`, `secret-definitions` and nested `jobs`. For `./…` refs the provider received `{path: ".github/workflows/deploy.yml"}` [ran]. **Only depth 0 or 1 is supported** (`LS@4043eda/workflow-parser/src/model/convert.ts#L31`). Remote refs parse to `{owner, repository, path, version}` (`workflow-parser/src/workflows/file-reference.ts#L14-L34`). We need our own provider for those, such as a fetch from the GitHub API or a user upload. Permission checks between caller and callee are among the skipped tests, so they are not implemented [read].
- **Matrix `include`/`exclude`:** **not expanded.** `strategy` stays a raw token [ran], and the reference test output also keeps it raw (`testdata/reader/matrix-basic.yml`) [read]. The language service only derives matrix *keys* for completion (`LS@4043eda/languageservice/src/context-providers/matrix.ts#L9`, doc comment L46–L97) [read]. A `${{ fromJSON(...) }}` matrix parses with no error and stays an expression [ran]. We build the Cartesian product plus include/exclude ourselves.
- **Schema validation errors** come with line and column. With the default `ErrorPolicy.ReturnErrorsOnly`, a parse error makes `convertWorkflowTemplate` return only `errors`. With `errorPolicy: ErrorPolicy.TryConversion` (value 1) it also reports converter-level errors: `Unexpected end of expression: '=='` (7:9), `Job 'b' depends on unknown job 'missing'` (11:12), and `The workflow must contain at least one job with no dependencies` for a needs cycle [ran]. `ErrorPolicy` is declared in `model/convert.d.ts` but not re-exported from the index, so pass the number or deep-import it [read].

## 6. Who uses them

- **`github/vscode-github-actions`** (the official VS Code extension, v0.32.3) depends on `@actions/languageserver ^0.3.60` and `@actions/workflow-parser ^0.3.60` ([`package.json` L585-L586](https://github.com/github/vscode-github-actions/blob/main/package.json)) [read].
- **`@actions/languageservice`** builds on both. Two pieces are worth borrowing: `context-providers/*.ts` builds the `github`, `needs`, `matrix`, `secrets` and other contexts as `DescriptionDictionary`s, and `utils/validate-if.ts` flags `if:` conditions like `format('push == {0}', …)` that are always true. That second check fits WhyNoRun's "explain the skip" job directly (`LS@4043eda/languageservice/src/utils/validate-if.ts#L19`) [read]. I found no consumer that *evaluates* a whole workflow run. That part is ours to build [inferred, from repo code search for `new Evaluator`: only `expressions/` and `languageservice/src/expression-hover/visitor.ts`].

## Verdict for the map

**Use both packages. They are the right foundation, and they run in the browser today. Treat them as a parser, validator and expression engine, not as a simulator.**

**What we get for free (high confidence, all run):**
- YAML → validated token tree with GitHub's own schema. Errors (unknown keys, bad cron, bad permission names, disallowed contexts, unknown `needs`, dependency cycles, malformed expressions) come with one-based line and column.
- Typed `on:` events and filters, jobs, `needs`, reusable-workflow calls (depth 1 through our `FileProvider`), and concurrency tokens.
- `if:` already normalized with GitHub's implicit `success() &&` wrap. Interpolated strings are rewritten into `format()` expressions.
- A zero-dependency expression evaluator that takes our own `github/inputs/vars/secrets/needs/matrix` contexts and accepts our own function implementations.
- A browser bundle of about 75 KB gzip under Vite. MIT/ISC licences.

**What we must build:**
1. **Status functions** (`success`, `failure`, `cancelled`, `always`), driven by the simulated `needs` results and concurrency outcome, plus a `hashFiles` stub for step-level `if`.
2. **Permissions model.** Read `permissions` and `defaults` from the raw token tree. The converter drops them, and caller/callee permission rules are not implemented.
3. **Matrix expansion** (product, `include`, `exclude`, `fromJSON` matrices driven by the scenario).
4. **Event and filter matching** (branch, tag and path globs; `types`; fork PR vs `pull_request_target` semantics).
5. **A position index for Verdicts.** Walk the raw tokens for filter lines, and fall back to the job key when an `if` is implicit.
6. **A FileProvider** for remote reusable workflows, and our own handling for depth > 1.
7. **A CLI build step** (esbuild bundle) until upstream issue #387 is fixed.

**Risks:**
- **Divergence from GitHub's real parser.** 93 shared conformance tests are skipped in the TS port, including permissions, matrix and reusable-workflow permissions. Mitigation: pin the exact version, add our own golden tests, and phrase Verdicts as "per GitHub's published parser".
- **Pre-1.0 API, deep imports and maintenance mode.** The upstream repo takes no contributions. Mitigation: wrap the library behind one adapter module in the core.
- **The Node ESM import bug (#387)** breaks a naive `node` CLI. The bundling workaround has been verified.
- **Bundle weight** (~75 KB gzip) is fine for a playground. Lazy-loading the parser keeps first paint light if needed [inferred].

**Unverified:** Vitest running the package directly (expected to work, because Vite handles JSON imports). Behaviour of versions newer than 0.3.61 (none existed on 2026-10-28). Whether `failure(jobId)` and `success(jobId)` arguments (allowed in `job-if`) need special handling in our stubs.
